Read this if you are installing the `prod` branch through Coolify.

# Coolify setup

Coolify uses this repository's Docker Compose file to run the website, PostgreSQL, Redis, and daily backups. On the first start, it copies Neon data into an empty PostgreSQL database. Later starts keep that database and apply any new migrations automatically.

## First deployment

1. **Connect the code.** In Coolify, connect the repository, select branch `prod`, choose **Docker Compose**, and set the Compose file to `/compose.prod.yaml`.
2. **Create storage folders.** On the Docker server, create `/data/ctiks-media` and `/data/ctiks-backups`. The app must be able to read and write the media folder as UID 1000. If you use different server paths, set `CTIKS_MEDIA_HOST_DIR` and `CTIKS_BACKUP_HOST_DIR` to those paths in Coolify.
3. **Enter these Production environment variables** in Coolify before deploying:

   | Name | Value |
   | --- | --- |
   | `POSTGRES_PASSWORD` | A new, long, URL-safe password for this PostgreSQL database. |
   | `BETTER_AUTH_SECRET` | A new random secret of at least 32 characters. |
   | `BETTER_AUTH_URL` | The exact public HTTPS address of the site, without a trailing slash. |
   | `SOURCE_DATABASE_URL` | Neon's **direct** PostgreSQL URL for the first import. Keep its `&` characters literal. |

   For a localhost-only test, use `BETTER_AUTH_URL=http://localhost:3000` and set `CTIKS_LOCAL_HTTP=1`. Do not use that flag for the public site. When importing Neon, leave `ADMIN_EMAIL` and `ADMIN_INITIAL_PASSWORD` unset: the admin account comes from Neon.

4. **Deploy and check.** In the `bootstrap` logs, look for `Transfer completed`; the job must exit successfully. Open the site and sign in with the imported admin account. If import fails, check the `bootstrap` logs before redeploying. You do not need to run a separate import or migration command.
5. **Finish the handover.** Remove `SOURCE_DATABASE_URL` from Coolify and redeploy. Copy existing images and PDFs into the media folder, keeping their filenames. Check that an existing image and PDF open, then confirm that the `backup` container reports `Backup ready`.

Coolify also displays database and Redis URLs generated by Compose. You do not need to enter those separately. Its **Preview deployments** list repeats settings for preview builds; it is not a second production setup. Normal redeploys retain the database volume, but deleting the Coolify resource can remove it.

## Backups in Coolify

The `backup` container saves the database and uploaded images/PDFs when it starts and every 24 hours after that. It retries failures after one hour. Each saved version has a **backup ID** such as `ctiks-20261105T065959Z-40068177`. The newest 14 routine versions are kept; a new one removes the oldest. Redis login sessions are not included. Copy backups to protected storage off the server too.

### Which ID and terminal?

| Term | What it means |
| --- | --- |
| Backup ID: `ctiks-...` | One saved version. Use this ID to test or restore that version. Find it with `list`. |
| Test database: `ctiks_restore_...` | A temporary copy created by `restore-test`. Use this name **only** with `cleanup-test`. It is not a backup ID. |
| Coolify resource ID | Coolify's ID for this deployment. Find it in the Coolify page URL or between `app-` and the final timestamp in a container name such as `app-RESOURCE_ID-20261105T063530`. A new Coolify resource gets a different ID. |
| **Backup container** terminal | Use for `list`, `run`, `restore-test`, and `cleanup-test`. Open the resource's Terminal and select its running `backup-...` container. |
| **Server** terminal | Use for a live restore. Select the server running Docker in Coolify's Terminal, or open that server's Linux shell. Do not select the `app`, `backup`, `postgres`, or `coolify` container. |

### 1. List or make a backup

In the **backup container** terminal, run:

```bash
node scripts/backup-manager.mjs list
```

The newest backup is first. Each row shows its ID, date, and media-file count. If it says `No completed backups are available yet`, wait for or make a backup. Do not restore a row marked `incomplete or unreadable`. An early backup may show `0 media files` if files were copied later. Keep each deployment's backup host folder separate so its list contains only its own backups.

To save the current site now, run this in the **same terminal**, then run `list` again:

```bash
node scripts/backup-manager.mjs run
```

Success says `Backup ready: ctiks-...`.

### 2. Optional: check that a backup can be restored

This is a **practice run**. It makes a temporary database and media copy to check the backup; the live website does not change. In the **backup container** terminal, replace `BACKUP_ID` with one exact `ctiks-...` ID from `list`:

```bash
node scripts/backup-manager.mjs restore-test BACKUP_ID
```

Success says `Restore check ready`, followed by a temporary name beginning `ctiks_restore_`. Copy **that temporary name** into the next command to remove the practice copy:

```bash
node scripts/backup-manager.mjs cleanup-test TEST_DATABASE_NAME
```

The saved `ctiks-...` backup remains. **The test does not roll back the website.** If the website is fine, stop here.

### 3. Restore a backup to the live website, only when needed

This replaces the live database **and** uploaded files with the chosen version. Plan downtime. Use the **server terminal**. Copy each command below without the numbered step text.

1. Set the two IDs. Replace the example resource ID with the ID of **this** Coolify resource, and replace `BACKUP_ID` with the chosen `ctiks-...` ID from `list`:

   ```bash
   CTIKS_RESOURCE_ID=RESOURCE_ID_FROM_COOLIFY
   BACKUP_ID=CHOSEN_CTIKS_BACKUP_ID
   ```

2. Open Coolify's deployed Compose folder. Check that both files exist, then confirm `ps` shows this resource's `app`, `backup`, `postgres`, and `redis` services. On this Coolify installation the folder is `/data/coolify/applications/RESOURCE_ID`:

   ```bash
   cd "/data/coolify/applications/$CTIKS_RESOURCE_ID"
   ls docker-compose.yaml .env
   docker compose -p "$CTIKS_RESOURCE_ID" -f docker-compose.yaml ps
   ```

3. Stop the website and automatic backups. Keep PostgreSQL and Redis running:

   ```bash
   docker compose -p "$CTIKS_RESOURCE_ID" -f docker-compose.yaml stop app backup
   ```

4. Restore the chosen backup. The command first saves today's live data as a protected safety backup. Wait for **`Live restore completed`**. If it fails, leave the site stopped and investigate:

   ```bash
   docker compose -p "$CTIKS_RESOURCE_ID" -f docker-compose.yaml run --rm --no-deps backup scripts/backup-manager.mjs restore-live "$BACKUP_ID" --apply
   ```

5. Start the app and check the website. App startup applies pending database migrations. Then restart automatic backups:

   ```bash
   docker compose -p "$CTIKS_RESOURCE_ID" -f docker-compose.yaml start app
   docker compose -p "$CTIKS_RESOURCE_ID" -f docker-compose.yaml start backup
   ```

Do not delete the PostgreSQL volume. Users may need to sign in again because Redis sessions are not restored. See [Storage and backups](PRODUCTION_HANDOVER.md) for backup location and retention.
